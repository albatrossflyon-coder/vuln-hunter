# GraphQL Resolver Implementation Plan - Phase 2: Findings Persistence

This plan addresses the ambiguity identified in `PLAN_GRAPHQL.md` regarding the `findings_for_scan` resolver, which requires persistent storage of individual findings.

## 1. New `findings` Table Schema

To store individual findings, a new table named `findings` will be added to `backend/telemetry.py`'s `init_db()` function. This table will be linked to the `scans` table via `scan_id` and will store the detailed information of each finding.

**`CREATE TABLE` statement for `findings`:**

```sql
CREATE TABLE IF NOT EXISTS findings (
    finding_id TEXT PRIMARY KEY, /* Use fingerprint from ignore_store.py as ID */
    scan_id TEXT NOT NULL REFERENCES scans(scan_id) ON DELETE CASCADE,
    rule_id TEXT NOT NULL,
    path TEXT NOT NULL,
    start_line INTEGER,
    end_line INTEGER,
    matched_code TEXT,
    snippet TEXT,
    severity TEXT,
    exploitability TEXT,
    message TEXT,
    triage_status TEXT,
    ai_reasoning TEXT,
    timestamp REAL NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_findings_scan_id ON findings(scan_id);
CREATE INDEX IF NOT EXISTS idx_findings_rule_id ON findings(rule_id);
```

**Justification for columns:**
*   `finding_id`: Uses the `fingerprint` generated by `ignore_store.py` for stable, content-based identification. This also helps with de-duplication and ignore-list integration.
*   `scan_id`: Foreign key referencing the `scans` table, allowing retrieval of findings for a specific scan.
*   `rule_id`, `path`, `start_line`, `end_line`, `matched_code`, `snippet`, `severity`, `exploitability`, `message`, `triage_status`, `ai_reasoning`: These fields directly map to common attributes of findings generated by the scanners and processed by triage. `matched_code` is crucial for fingerprinting; `snippet` provides context.
*   `timestamp`: Records when the finding was recorded, useful for auditing and sorting.

## 2. Modifications to `record_scan_results()` in `backend/telemetry.py`

The `record_scan_results()` function currently processes a list of findings to update `scanner_metrics`. It needs to be extended to also insert each individual finding into the new `findings` table.

**Changes:**

1.  **Import `fingerprint`:** Add `from ignore_store import fingerprint` at the top of `telemetry.py`.
2.  **Iterate and Insert:** Within the `with _connect() as conn:` block, after the `scanner_metrics` insertions, iterate through the `findings` list (the original argument to `record_scan_results`). For each finding:
    a.  Generate its `finding_id` using `fingerprint(f)`.
    b.  Prepare the data for insertion, ensuring all columns of the `findings` table are populated. Default or `None` values can be used for optional fields if the finding dictionary doesn't contain them.
    c.  Execute an `INSERT OR REPLACE` statement into the `findings` table. `OR REPLACE` is chosen to handle potential re-processing of the same finding (e.g., if a scan is re-run) without causing primary key conflicts, effectively updating the finding if it already exists.

**Example `INSERT` statement within `record_scan_results()` loop:**

```python
# Inside the loop over `findings` (the original argument)
# f is a single finding dictionary
finding_id = fingerprint(f)
conn.execute(
    "INSERT OR REPLACE INTO findings (finding_id, scan_id, rule_id, path, start_line, end_line, matched_code, snippet, severity, exploitability, message, triage_status, ai_reasoning, timestamp) "
    "VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)",
    (
        finding_id,
        scan_id,
        f.get("rule_id", ""),
        f.get("path", ""),
        f.get("start_line"),
        f.get("end_line"),
        f.get("matched_code"),
        f.get("snippet"),
        f.get("severity"), # Or f.get("exploitability") if severity is not directly available
        f.get("exploitability"),
        f.get("message"),
        f.get("triage_status"),
        f.get("ai_reasoning"),
        time.time(),
    ),
)
```

## 3. `findings_for_scan(self, scan_id: strawberry.ID) -> list[Finding]` Query

This resolver in `backend/schema.py` will now query the newly created `findings` table in `backend/telemetry.py`.

**Proposed Query and Logic in `findings_for_scan`:**

1.  Add a new function to `backend/telemetry.py`, e.g., `get_findings_by_scan_id(scan_id: str) -> List[Dict[str, Any]]`.
    *   This function would use `_connect()` and execute a `SELECT * FROM findings WHERE scan_id = ?` query, returning a list of dictionaries.
    *   **Consideration:** Integrate `ignore_store.filter_ignored()` here. If the goal is to only show *active* findings (not ignored ones), `get_findings_by_scan_id` should fetch the `repo_path` for the `scan_id` (from the `scans` table), then use that `repo_path` with `filter_ignored` on the retrieved findings.

2.  In `schema.py`, the `findings_for_scan` resolver would:
    a.  Call `telemetry.get_findings_by_scan_id(str(scan_id))`.
    b.  For each finding dictionary returned, construct a `Finding` object.

**Example `get_findings_by_scan_id` function (to be added to `backend/telemetry.py`):**

```python
# (add imports: from typing import List, Dict, Any, Optional; import ignore_store)

def get_findings_by_scan_id(scan_id: str) -> List[Dict[str, Any]]:
    reconcile_stale() # Ensure scan statuses are up to date
    with _connect() as conn:
        # First, get the repo_path to use with ignore_store.filter_ignored
        scan_row = conn.execute("SELECT repo_path FROM scans WHERE scan_id = ?", (scan_id,)).fetchone()
        if not scan_row:
            return []
        repo_path = scan_row["repo_path"]

        # Fetch all findings for the scan
        raw_findings = conn.execute(
            "SELECT finding_id, rule_id, path, start_line, end_line, matched_code, snippet, severity, exploitability, message, triage_status, ai_reasoning FROM findings WHERE scan_id = ?",
            (scan_id,)
        ).fetchall()
        
        findings_list = [dict(f) for f in raw_findings]
        
        # Attach fingerprints and filter ignored findings
        # Note: filter_ignored expects 'rule_id', 'path', 'matched_code' in findings
        # Ensure 'finding_id' from the DB is re-attached as 'fingerprint' if needed for schema.py
        processed_findings = ignore_store.filter_ignored(repo_path, findings_list)
        
        return processed_findings
```

**Type Mapping in `schema.py` (assuming `get_findings_by_scan_id` returns dictionaries):**

*   `Finding.id`: Map from `finding["finding_id"]` (or `finding["fingerprint"]` if `filter_ignored` renames it) to `strawberry.ID()`.
*   `Finding.scan_id`: Map from the input `scan_id` (already known).
*   `Finding.title`: Map from `finding["message"]` or `finding["rule_id"]`.
*   `Finding.severity`: Map from `finding["severity"]` or `finding["exploitability"]`.

**Ambiguities:**
*   **`Finding.title` mapping:** The `Finding` GraphQL type has a `title`. In the raw finding data, there might be a `message` or `rule_id` that can serve as a title. The plan proposes `message` or `rule_id`, but a decision will be needed during implementation for the preferred field. `severity` and `exploitability` might need to be consolidated into a single `severity` field for the GraphQL type if both are present in the raw data.
*   **Integration of `ignore_store.filter_ignored`**: The proposed `get_findings_by_scan_id` includes `filter_ignored`. This ensures only active findings are returned. This is a design choice that can be revisited if ignored findings ever need to be specifically queried (e.g., for an "ignored findings" view). Currently, the `Finding` type does not explicitly support an "ignored" status.
